# TLS Blueprint for `hajnal.space` Subdomains

Portable recipe for giving any new service working TLS on the `hajnal.space`
zone. The origin uses a **self-signed** certificate generated by the service's
deployment script; Cloudflare Universal SSL provides the publicly-trusted edge
certificate. No Let's Encrypt, ACME, or cert-manager dependency.

## TL;DR

End users **do not** see the origin's certificate. They see **Cloudflare
Universal SSL** — a zone-wide wildcard for `hajnal.space` + `*.hajnal.space`
that Cloudflare issues and renews automatically. To get working TLS for a new
subdomain you need to:

1. **DNS** — point the subdomain at Cloudflare (proxied / "orange cloud").
   This alone gives you free, valid edge TLS.
2. **Origin** — give the origin a self-signed certificate for that subdomain.
   Cloudflare in `Full` mode does not validate the origin cert — it only
   requires that the origin speaks TLS.

The origin cert is for the **Cloudflare → origin** hop, not for end users.

> **Required Cloudflare SSL/TLS mode: `Full`.** Do **not** use `Full (strict)`
> (it validates the origin cert and will reject the self-signed certificate
> with error 526). Do **not** use `Flexible` (it allows plain-HTTP origin
> traffic, which breaks HSTS and the HTTPS-only OAuth flow).

## How `hajnal.space` is signed (analysis)

Live observation (2026-08-21):

| Check | Result |
|---|---|
| `dig A sentinel.hajnal.space` | `172.67.x`, `104.21.x`, `2a06:98c1::` — all **Cloudflare** anycast |
| `dig A cal.hajnal.space` / `mcal.hajnal.space` | `188.114.96.0/20` — also **Cloudflare** (`CLOUDFLARENET-EU`) |
| Edge cert `subject` | `CN=hajnal.space` |
| Edge cert `issuer` | `Google Trust Services / WE1` (root `GTS Root R4`) |
| Edge cert `SAN` | `DNS:hajnal.space, DNS:*.hajnal.space` |
| Edge cert validity | 90 days, auto-renewed by Cloudflare |
| Cert serial (sentinel / cal / mcal) | **identical** — one shared zone wildcard |
| `curl -I https://…` headers | `server: cloudflare`, `cf-ray: …` |

Conclusion: the whole `hajnal.space` zone is fronted by Cloudflare. The
end-user-facing certificate is **Cloudflare Universal SSL** (a wildcard), not
a per-domain certificate. That is why "the cert is working" with zero
per-subdomain effort.

### The two TLS hops

```
 ┌────────┐   TLS #1 (end user)    ┌─────────────┐   TLS #2 (origin hop)   ┌──────────────┐
 │ Client │ ─────────────────────▶ │  Cloudflare │ ───────────────────────▶ │ k3s / Traefik│
 └────────┘   Universal SSL        │     edge    │   Full (not strict)      │    origin    │
              wildcard             └─────────────┘   self-signed origin     └──────────────┘
              hajnal.space +             │           cert (365 days)              │
              *.hajnal.space             │           generated by deploy          │
              issued by GTS,             ▼           script                       ▼
              auto-renewed            (L7 proxy to origin IP)              serves cert from
                                                                              <service>-tls Secret
```

- **TLS #1** is what browsers validate. Cloudflare owns it. Nothing to manage.
- **TLS #2** is the Cloudflare-to-origin hop. Cloudflare in `Full` mode does
  **not** validate this certificate — it only requires that the origin speaks
  TLS. The self-signed cert satisfies that requirement.

## Blueprint for a new repo / service

Assume a new subdomain `<name>.hajnal.space` and a Kubernetes namespace `<ns>`.

### Step 0 — Prerequisites

- Cloudflare zone `hajnal.space` with SSL/TLS mode set to **`Full`**.
- A Kubernetes cluster with an ingress controller (Traefik in this repo).
- `openssl` available on the deployment host (for certificate generation).

No cert-manager, Let's Encrypt, or ACME account is required.

### Step 1 — DNS: point the subdomain at Cloudflare

In the Cloudflare dashboard (or API) for zone `hajnal.space`:

- Add record `<name>` → type `A`/`AAAA` (or `CNAME`) → **Proxied** (orange cloud).
- Keep the record pointing at the origin's public endpoint (the same one
  `sentinel` / `cal` / `mcal` use).

This single step is what makes the **edge** certificate valid. Cloudflare's
Universal SSL already covers `*.hajnal.space`, so no cert work is needed here.

### Step 2 — Edge TLS: nothing to do

Cloudflare terminates TLS #1 with the zone wildcard. Verify, don't configure:

```bash
openssl s_client -connect <name>.hajnal.space:443 \
  -servername <name>.hajnal.space </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -subject -dates
# expect: issuer=Google Trust Services / WE1, subject=CN=hajnal.space
```

### Step 3 — Origin TLS (self-signed)

Generate a self-signed certificate covering the subdomain and store it in a
Kubernetes TLS Secret.

**3a. Generate the certificate and key:**

```bash
# Generate a self-signed RSA 2048-bit certificate with SANs
openssl req -x509 -nodes -newkey rsa:2048 -days 365 \
  -keyout /tmp/<name>-tls.key \
  -out /tmp/<name>-tls.crt \
  -subj "/CN=<name>.hajnal.space" \
  -addext "subjectAltName=DNS:<name>.hajnal.space"
```

For multiple domains (like this repo's `cal` + `mcal`):

```bash
openssl req -x509 -nodes -newkey rsa:2048 -days 365 \
  -keyout /tmp/stack-tls.key \
  -out /tmp/stack-tls.crt \
  -subj "/CN=cal.hajnal.space" \
  -addext "subjectAltName=DNS:cal.hajnal.space,DNS:mcal.hajnal.space"
```

**3b. Create the Kubernetes TLS Secret:**

```bash
kubectl create secret tls <name>-tls \
  --cert=/tmp/<name>-tls.crt \
  --key=/tmp/<name>-tls.key \
  --dry-run=client -o yaml | kubectl apply -f -
```

Or for the shared multi-domain secret:

```bash
kubectl create secret tls commoncal-tls \
  --cert=/tmp/stack-tls.crt \
  --key=/tmp/stack-tls.key \
  -n <ns> \
  --dry-run=client -o yaml | kubectl apply -f -
```

**3c. Ingress** referencing that secret:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: <name>
  namespace: <ns>
  annotations:
    traefik.ingress.kubernetes.io/router.entrypoints: websecure
spec:
  ingressClassName: traefik
  tls:
    - secretName: <name>-tls
      hosts:
        - <name>.hajnal.space
  rules:
    - host: <name>.hajnal.space
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: <name>
                port:
                  number: 80
```

> **No cert-manager annotation.** Do not add
> `cert-manager.io/cluster-issuer` — this design uses a pre-generated
> self-signed Secret, not cert-manager.

### Step 4 — Verify

```bash
# Secret exists and is the correct type
kubectl get secret <name>-tls -n <ns> -o jsonpath='{.type}'
# Expected: kubernetes.io/tls

# Inspect the origin certificate from the Secret
kubectl get secret <name>-tls -n <ns> \
  -o jsonpath='{.data.tls\.crt}' | base64 -d \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# End-user-side: edge cert is the Cloudflare wildcard
openssl s_client -connect <name>.hajnal.space:443 \
  -servername <name>.hajnal.space </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -subject -ext subjectAltName

# Full chain validates (browser perspective)
curl -sI https://<name>.hajnal.space | grep -iE 'HTTP/|server'

# Origin-side: connect to the origin IP directly (bypassing Cloudflare) to
# confirm Traefik presents the self-signed cert. Requires the origin's
# public IP (the k3s node, not the Cloudflare anycast).
ORIGIN_IP=<origin-public-ip>
openssl s_client -connect "$ORIGIN_IP":443 \
  -servername <name>.hajnal.space </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
# expect: subject=CN=<name>.hajnal.space, issuer=CN=<name>.hajnal.space (self-signed)
```

## Caveats

- **Cloudflare SSL mode must be `Full`.**
  - `Full` → self-signed origin is accepted. **← required for this design.**
  - `Full (strict)` → origin needs a publicly-trusted cert. **Incompatible**
    with the self-signed origin; causes Cloudflare error 526.
  - `Flexible` → origin may be plain HTTP (not recommended; breaks HSTS and
    the HTTPS-only OAuth flow).
- **The self-signed cert is not publicly trusted.** Browsers never see it —
  they see Cloudflare Universal SSL. Only the Cloudflare-to-origin hop uses
  the self-signed cert, and Cloudflare in `Full` mode does not validate it.
- **The edge wildcard is not something you can "add a domain to."** It already
  covers every `*.hajnal.space`. A new subdomain works the moment its DNS is
  proxied.
- **Apex + wildcard:** the zone cert covers both `hajnal.space` and
  `*.hajnal.space`, but **not** multi-level labels like `a.b.hajnal.space`
  (a single `*` matches one label only). For deep subdomains you need an
  explicit edge cert (Cloudflare Advanced Certificate) — out of scope here.
- **Certificate expiry:** the self-signed cert is valid for 365 days. The
  deploy script in this repo enforces a 30-day expiry guard and regenerates
  the cert when it is about to expire. For other services, set up a calendar
  reminder or cron job to regenerate the cert before it expires.
- **Different origin cluster:** if the new service runs on a *different* k3s
  cluster, that cluster also needs the self-signed Secret and its Traefik must
  be reachable through the same proxied DNS record. No cert-manager or ACME
  account is needed on either cluster.

## Reference: what this repo does

- `deploy/deploy-prod.sh` — generates a self-signed RSA 2048-bit / SHA-256
  certificate (365 days) covering both `cal.hajnal.space` and
  `mcal.hajnal.space` on first run, stores it in the `commoncal-tls` Secret,
  and reuses it on subsequent runs (with a 30-day expiry guard).
- `deploy/flux/overlays/production/charts/core-helmrelease.yaml` — the core
  Ingress references the shared `commoncal-tls` Secret covering
  `cal.hajnal.space` + `mcal.hajnal.space`; the MCP Ingress references the
  same Secret.
- `docs/DEPLOYMENT.md` — full Flux/Helm deployment contract with TLS
  verification and rollback instructions.
